# AI 代理工具懶人包

> 聊天視窗以外的另一類 AI 工具：能讀寫你的檔案、跑你的指令、把重複的流程固化成可重用的模組。這一頁講它們在研究工作裡實際能做什麼。

---

## 一、先分清楚三類工具

| 類型 | 代表 | 能碰到什麼 | 適合的任務 |
|---|---|---|---|
| **聊天介面** | ChatGPT、Claude、Gemini 的網頁版 | 只有你貼進去的內容 | 問答、腦力激盪、改一段文字 |
| **深度研究模式** | 各家的 Deep Research | 網路 + 你上傳的檔案 | 環境掃描、帶引用的長篇報告 |
| **代理型 CLI／IDE 工具** | Claude Code、OpenAI Codex、Gemini CLI、Cursor | **你的整個資料夾**：讀檔、寫檔、跑指令、多步驟自主執行 | 跨檔案的批次作業、可重複的流程、資料處理 |

第三類的關鍵差異只有一句話：

> **前兩類幫你想，第三類幫你做，而且是在你的檔案上做。**

這也是它風險最高的地方。它能改的檔案就是你論文的檔案。

!!! warning "用代理型工具的第一條規矩：版本控制"
    在讓任何代理工具動你的論文資料夾之前，先把它變成 git repo，或至少確保有一份完整備份。
    `repo` 就是放置整個專案檔案的資料夾；`commit` 是替目前版本留一個可回復的存檔點，`diff` 則是查看前後改了哪些內容。
    **能自動改一百個檔案的工具，也能自動改壞一百個檔案。**

## 二、Claude Code

### 2.1 它是什麼

一個跑在終端機（也有 IDE 擴充與桌面版）的代理工具。你給它一個資料夾，它可以讀裡面的檔案、執行指令、修改內容，並且把多步驟的工作連貫做完。

原本是給寫程式用的，但它處理的其實是**「一批檔案 + 一套規則」**這個通用問題。論文資料夾、文獻筆記庫、問卷資料，全都符合這個形狀。

### 2.2 四個擴充機制

Claude Code 的可客製化程度來自四個東西，由淺入深：

| 機制 | 是什麼 | 什麼時候用 |
|---|---|---|
| **CLAUDE.md** | 放在專案根目錄的說明檔，每次啟動都會被讀進去 | 記錄**事實**：這個專案是什麼、檔案怎麼放、有什麼規矩 |
| **Skill** | 一個 `SKILL.md`，寫一套**程序** | 你一直在貼同樣的指示、同樣的檢查清單 |
| **Subagent** | 有自己系統提示詞與工具限制的子代理 | 需要一個獨立、乾淨的視角（例如「批判性審稿人」） |
| **Plugin** | 把上面這些打包成可安裝、可分享、可版本控制的一包 | 想跨專案重用，或分享給同學／實驗室 |

**CLAUDE.md 與 Skill 的分工**是最常搞混的：CLAUDE.md 放**事實**（會一直佔用脈絡），Skill 放**程序**（只有用到時才載入，所以長篇的參考資料放在 skill 裡幾乎不花成本）。

當你發現 CLAUDE.md 裡某一段已經長成一套步驟而不是一條事實，那一段就該搬進 skill。

### 2.3 Skill 的最小結構

一個 skill 就是一個資料夾裡的 `SKILL.md`：

```
.claude/skills/tw-style-check/SKILL.md
```

```markdown
---
description: 檢查繁體中文學術寫作的用語與因果動詞紀律。當使用者要求檢查論文段落、
  或提到「用語檢查」「去 AI 感」「大陸用語」時使用。
---

# 台灣學術用語與因果動詞檢查

對使用者提供的段落執行下列檢查，逐項列出「行號 + 原句 + 問題 + 建議改法」。
**只診斷，不要直接改寫，除非使用者明確要求。**

## 一、因果動詞（橫斷面研究）
掃描：導致、造成、引發、決定、促使形成、固化為、讓⋯⋯變得
判斷規則：
- 若該句是在報告**本研究的橫斷面結果** → 必須改成「預測」「與⋯⋯相關」
- 若該句是在**引用他人的實驗或縱貫研究** → 保留因果動詞，但要確認引文標示清楚

## 二、大陸用語
掃描並對照建議：
被試→受試者／填答者、數據收集→資料蒐集、信息→資訊、回歸→迴歸、
結果表明→結果顯示、人工智能→人工智慧、用戶→使用者、算法→演算法、
數據庫→資料庫、優化→最佳化、場景→情境、聚合效度→收斂效度、
橫截面→橫斷面、縱向→縱貫、方差→變異數、置信區間→信賴區間

## 三、AI 套話
掃描：換句話說、換言之、綜上所述、值得注意的是、具有重要意涵、填補研究缺口
規則：「值得注意的是」全篇最多兩次；其餘建議刪除或改寫為具體內容。

## 四、句長變異
若連續三句字數相差在 4 字以內，標記為「句長過於一致」，建議插入短句或長句。

## 輸出格式
用表格輸出：| 行號 | 原句 | 問題類型 | 建議 |
最後給一段總評：這一節最需要優先處理的三個問題是什麼。
```

存好之後，在對話裡打 `/tw-style-check` 就會執行；或者你只是說「幫我檢查這段的用語」，Claude 也會自己判斷要用它。

**這就是「把你自己的檢查清單變成可執行的東西」**。本站[學術中文寫作紀律](style.md)那一頁的內容，剛好就是一份 skill 的原料。

### 2.4 Plugin：把 skill 打包分享

當你的 skill 累積到值得分享時，可以打包成 plugin。結構是：

```
my-research-kit/
├── .claude-plugin/
│   └── plugin.json          ← 只有這個檔案放在 .claude-plugin/ 裡
├── skills/
│   ├── tw-style-check/SKILL.md
│   ├── lit-matrix/SKILL.md
│   └── citation-verify/SKILL.md
├── agents/                  ← 自訂子代理
├── hooks/hooks.json         ← 事件觸發的自動化
├── .mcp.json                ← 外部工具連接設定
└── README.md
```

`plugin.json` 最少只要三個欄位：

```json
{
  "name": "my-research-kit",
  "description": "碩論寫作的檢查與整理工具組",
  "version": "1.0.0"
}
```

常用指令：

| 指令 | 作用 |
|---|---|
| `claude plugin init my-tool` | 在 skills 目錄下建立一個 plugin 骨架，下次啟動自動載入 |
| `claude --plugin-dir ./my-plugin` | 開發時直接載入本地 plugin 測試（不用安裝） |
| `/reload-plugins` | 改完之後重新載入，不必重開 |
| `claude plugin validate ./my-plugin` | 驗證結構是否正確 |
| `/plugin` | 開啟 plugin 管理介面（安裝、停用、看錯誤） |

**兩個容易踩的坑**：

1. **只有 `plugin.json` 放在 `.claude-plugin/` 裡**，`skills/`、`agents/`、`hooks/` 都要放在 plugin 根目錄。
2. plugin 的 skill 一律加上命名空間，叫做 `/my-research-kit:tw-style-check`，避免和別人的同名 skill 撞名。

想安裝別人做好的，Anthropic 維護兩個公開市集：官方策展的 `claude-plugins-official`，以及社群審核後上架的 `claude-community`（用 `/plugin marketplace add anthropics/claude-plugins-community` 加入）。

### 2.5 MCP：把外部工具接進來

MCP（Model Context Protocol）讓 Claude Code 連到外部服務。研究情境常見的接法：

- **文獻管理器**（例如 Zotero 的 MCP server）：讓 AI 直接查你自己的文獻庫，而不是憑空生成引用
- **檔案系統／雲端硬碟**：存取論文資料夾
- **資料庫**：直接查你的問卷原始資料
- **瀏覽器**：抓取指定網頁

!!! tip "為什麼接上自己的文獻庫是最有價值的一步"
    AI 幻覺文獻的根本原因是「它沒有你的文獻庫，只好用生成的」。
    一旦它能查詢你真的收藏過的條目，「捏造引用」的機率會大幅下降，因為它有真的東西可以引。

## 三、OpenAI Codex

### 3.1 定位

OpenAI 的編碼代理，包含在 ChatGPT 的 Plus、Pro、Business、Edu 與 Enterprise 方案中。

官方列出的能力：程式碼生成、理解陌生或既有的程式碼、程式碼審查（找潛在錯誤與邊界情況）、除錯與根因診斷、以及重構／測試／遷移這類重複性工作的自動化。

### 3.2 可用介面

| 介面 | 用途 |
|---|---|
| **CLI** | 終端機，最接近 Claude Code 的用法 |
| **IDE 擴充** | 在編輯器裡直接用 |
| **App（桌面）** | 圖形介面 |
| **Web** | 雲端執行，適合長時間任務 |
| **整合** | GitHub、Slack、Linear |

### 3.3 AGENTS.md

Codex 用 `AGENTS.md` 作為專案層級的代理設定檔，角色類似 Claude Code 的 `CLAUDE.md`：把專案的規則、慣例與注意事項寫進去，每次執行都會被讀到。

**一個研究專案的 `AGENTS.md` 骨架**（`CLAUDE.md` 也適用，換個檔名即可）：

```markdown
# 專案：碩士論文

## 這個資料夾是什麼
- `chapters/` 論文各章的 Markdown 原稿
- `refs/` 文獻筆記，每篇一個檔，檔名為 `作者年份-關鍵詞.md`
- `data/` 問卷原始資料與分析腳本（**這個資料夾禁止修改原始檔**）
- `figures/` 圖表輸出

## 寫作規則
- 繁體中文，台灣學術用語。禁用大陸用語（見 `docs/用語對照.md`）
- 本研究是橫斷面設計：描述本研究結果一律用「預測」「相關」，
  禁用「導致」「造成」「引發」。引用他人實驗時才可用因果動詞
- 引用格式 APA 7 中文化：中文用「等人」與「與」，頁碼用 en dash
- 每個構念全篇只能有一個中文譯名

## 絕對不要做的事
- 不要生成任何我沒有給你的文獻引用。找不到就說找不到
- 不要修改 `data/raw/` 底下的任何檔案
- 不要替我寫完整的論述段落。你可以診斷、可以列出問題、可以提供改寫選項，
  但最終的句子由我自己寫

## 我常請你做的事
- 檢查一節的用語與因果動詞紀律
- 把 `refs/` 底下指定的幾篇整理成文獻比較表
- 檢查某一章的結論有沒有回應緒論的研究問題
```

**最後兩個區塊比前面重要。** 「絕對不要做的事」是你的[邊界](ai-workflow.md)，它決定了工具會不會替你製造麻煩。

## 四、其他常見的代理型工具

| 工具 | 定位 | 研究情境的用法 |
|---|---|---|
| **Gemini CLI** | Google 的終端機代理 | 與 Google 生態（Drive、Docs）整合較順 |
| **Cursor / Windsurf** | AI 優先的編輯器 | 適合習慣圖形介面、需要看 diff 才安心的人 |
| **GitHub Copilot** | 編輯器內的補完與對話 | 寫分析腳本時的即時輔助 |
| **Jupyter + AI 擴充** | 資料分析筆記本 | 統計分析與圖表生成 |

**選哪一個不重要，重要的是三件事**：能不能限定它的工作範圍、能不能看到它改了什麼、能不能還原。

## 五、研究情境的十個實際應用

以下每一個都假設你已經把論文資料夾交給代理工具，而且**已經有版本控制**。

| # | 情境 | 怎麼下指令 | 為什麼值得交給它 |
|---|---|---|---|
| 1 | **全篇用語稽核** | 「掃描 `chapters/` 底下所有檔案，找出大陸用語與橫斷面研究不該用的因果動詞，用表格列出檔名、行號、原句、建議」 | 人工做會漏，而且做不了第二次 |
| 2 | **術語一致性檢查** | 「檢查全篇有沒有同一個構念用了兩個不同的中文譯名」 | 這是口試委員最容易抓到、你最容易忽略的問題 |
| 3 | **引用交叉核對** | 「比對 `chapters/` 內文的所有引註與 `references.md` 的清單，列出：內文有但清單沒有的、清單有但內文沒引的」 | 純機械工作，人做極慢且易錯 |
| 4 | **文獻筆記轉比較表** | 「讀 `refs/` 底下這 12 個檔案，整理成一張表：作者年份、理論、方法、樣本、主要結果、研究限制」 | [文獻比較表](literature.md)的半自動版 |
| 5 | **結論對照研究問題** | 「把第一章的研究問題和第五章的結論並排比對，指出哪一題沒有被明確回應」 | 最致命的結構性缺陷，也最難自己看出來 |
| 6 | **邏輯斷鏈診斷** | 「對第二章第三節做論證結構診斷：抽出命題、標出跳步與隱含前提」 | 見[AI 輔助研究工作流](ai-workflow.md)的研究教練角色 |
| 7 | **資料前處理腳本** | 「寫一個 Python 腳本，把 `data/raw/survey.csv` 依照這些規則清理，輸出到 `data/clean/`，**不要動原始檔**」 | 腳本可重跑、可檢查，比手動改 Excel 可靠得多 |
| 8 | **圖表批次產生** | 「用 `data/clean/` 產生這五張圖，統一用這組配色與字型，輸出 300dpi PNG 到 `figures/`」 | 統一格式，改一次全部重跑 |
| 9 | **格式套用** | 「把 `chapters/` 的 Markdown 依照系所模板轉成 Word，套用指定樣式」 | 排版是最不值得手工做的事 |
| 10 | **口試模擬** | 「用 `agents/` 裡的『嚴格口試委員』子代理，針對第三章提出最尖銳的十個問題」 | 子代理有獨立視角，不會被前面的對話帶著走 |

!!! note "注意第 7 到第 9 項的共同點"
    它們產出的是**腳本或流程**，不是一次性的結果。
    這就是代理型工具真正的價值：**你得到的是一個可以重跑的東西**，而不是一份改一次就要重做一次的輸出。

## 六、起手式：一個可用的專案結構

```
thesis/
├── CLAUDE.md              # 或 AGENTS.md：專案事實 + 規則 + 紅線
├── .claude/
│   └── skills/
│       ├── tw-style-check/SKILL.md     # 用語與動詞紀律檢查
│       ├── cite-audit/SKILL.md         # 引用交叉核對
│       └── lit-matrix/SKILL.md         # 文獻筆記轉比較表
├── chapters/
├── refs/
├── data/
│   ├── raw/               # 唯讀
│   └── clean/
├── figures/
└── .git/
```

**建置順序建議**：

1. 先建 git repo（沒有這一步，其他都不要做）
2. 寫 `CLAUDE.md`，特別是「絕對不要做的事」
3. 用一兩週，把你重複貼的指示記下來
4. 重複三次以上的，才變成 skill
5. skill 累積到五個以上、而且你想分享時，才打包成 plugin

**不要一開始就設計一套完整的系統。** 你還不知道自己會重複做什麼。

## 七、風險與邊界

### 7.1 技術風險

| 風險 | 對策 |
|---|---|
| 改壞檔案 | git；`data/raw/` 設唯讀；重要操作前先 commit |
| 悄悄改了你沒要它改的地方 | 每次都看 diff，不要盲目接受 |
| 幻覺引用寫進論文 | 三步查核；接上自己的文獻庫 |
| 敏感資料外流 | 受訪者資料先去識別化；確認同意書涵蓋範圍 |
| 安裝來路不明的 plugin | plugin 可以執行指令。只安裝你信任的來源 |

### 7.2 學術風險

代理工具讓「產出」變得非常快，這正是它對學位論文最危險的地方。

三條線：

1. **它可以幫你檢查，不該幫你論述。** 診斷、列問題、提供選項可以；替你寫出你講不清楚的段落不行。
2. **它產出的每一行，你都要能防守。** 口試委員指著任何一句問「你為什麼這樣寫」，你答不出來就是紅燈。
3. **揭露範圍要誠實。** 用了代理工具做資料清理、格式轉換、用語檢查，該寫進[AI 使用聲明](ethics.md)就寫進去。

!!! danger "最容易失守的一步"
    請它「把這一節改得更通順」，然後直接採用。
    改完之後你如果講不清楚那段的邏輯，代表**這段內容本質上還不是你的知識**。這時候該退回去重讀文獻，不是繼續潤飾。

## 八、本頁重點回顧

- 三類工具：聊天幫你想、深度研究幫你查、**代理型幫你做**，而且是在你的檔案上做。
- 用代理工具前，先有 git 或完整備份。
- CLAUDE.md／AGENTS.md 放**事實與紅線**；Skill 放**程序**。
- Skill 就是把你自己的檢查清單變成可執行的東西。
- Plugin 是把 skill 打包分享；只有 `plugin.json` 放在 `.claude-plugin/` 裡。
- MCP 接上自己的文獻庫，是降低幻覺引用最有效的一招。
- 最值得交給它的十件事，共同點是**機械、重複、可驗證**。
- 產出腳本比產出結果有價值，因為腳本可以重跑。
- 它可以幫你檢查，不該幫你論述；你講不清楚的段落就不該留在論文裡。
