把教材做成可安裝的 SKILL

從架構決策到 marketplace 上架：兩個 SKILL 的完整實作紀錄與可照抄的步驟

這一頁記錄一次真實發生的改造：把這個網站的一部分內容，從「同學自己複製貼上的提示詞」，變成兩個真正能用 /plugin install 裝進 Claude Code 的 SKILL。前半段是故事，包含一次規則被實務經驗糾正的真實教訓，都沒有美化；後半段是一套你可以照抄的步驟。

一、起點：為什麼要做這件事

AI 提示詞範本那一頁本來就提過一句話：同一類任務連續貼第三次同樣的提示詞，就該包成 SKILL。 AI 代理工具懶人包也介紹過 SKILL 與 Plugin 這兩個機制的基本結構。但這些都只是「講」，網站上實際能裝的東西只有零。

於是決定親自做一次，順便把整個過程寫下來——這頁本身，就是「SKILL 介紹」章節的一個實戰案例。

二、先搞懂兩個概念：SKILL 與 Plugin 到底是什麼

兩個名詞的規格細節——SKILL 的最小結構、plugin.json 的必填欄位、plugin 的資料夾配置——統一寫在AI 代理工具懶人包的「Skill 的最小結構」與同頁的 Plugin 一節，這裡不重複。以下只講這兩個機制在這次案例裡實際扮演的角色。

2.1 SKILL：一個資料夾，裝的是「程序」不是「事實」

一個 SKILL 最小就是一個資料夾裡放一個 SKILL.md，檔案開頭的 frontmatter 寫 name 與 description。這次的案例除了 SKILL.md，還多開一層 references/ 放判準表與檢查清單：

skills/research-question-audit/
├── SKILL.md
└── references/
    ├── gap-and-innovation.md
    ├── question-forms.md
    └── audit-checklist.md

觸發機制的關鍵是 description，而且運作方式是分層展開的（progressive disclosure）：對話一開始，Claude 只會先讀進所有已安裝 SKILL 的 name 與 description 這種輕量摘要，不會整份 SKILL.md 都先塞進脈絡；只有判斷目前任務跟某個 description 描述的情境相符，才會把那份 SKILL.md 的完整內容展開讀進來；再往下，SKILL.md 裡如果指到 references/ 底下的補充檔案，也是等真的需要引用時才展開讀取。這也是這次兩個 SKILL 都能把完整的判準表、例句庫、檢查清單整份放進 references/ 的原因——平常這些內容完全不佔用對話的脈絡空間，只有真的用到的那一份才會被讀進來。

description 寫得好不好，直接決定 Claude 會不會在對的時機自動叫用這個 SKILL、會不會在不該用的時候誤觸發。這也是後面第六節要專門跑評測的原因之一。

2.2 Plugin：把多個 SKILL 包起來，變成可安裝、可分享的單位

一個 SKILL 只是本機資料夾，別人沒辦法直接「安裝」它。要讓它可以被安裝、可以版本控制、可以分享出去，就要包成 plugin——一個 .claude-plugin/plugin.json 加上放在根目錄的 skills/（欄位與資料夾配置見 AI 代理工具懶人包的 Plugin 一節）。這裡只需要記住一件事：一個 plugin 底下可以放不只一個 SKILL，這次的案例就是同一個 plugin（thesis-toolkit）底下放了 research-question-audit 與 academic-writing-discipline 兩個 SKILL 資料夾。

要讓同學裝得到，還需要再包一層：marketplace。 Marketplace 是一個獨立的 repo，裡面 .claude-plugin/marketplace.json 列出這個 marketplace 收錄哪些 plugin、各自的原始碼在哪裡。使用者的安裝流程分兩步：先把 marketplace 加進自己的 Claude Code（/plugin marketplace add <repo擁有者>/<marketplace repo>），再從這個 marketplace 裡挑要裝的 plugin（/plugin install <plugin名稱>@<marketplace名稱>）。

這次實際的案例，就是開一個獨立的 marketplace repo，裡面用 plugins/ 子目錄放一個 plugin（thesis-toolkit），這個 plugin 底下的 skills/ 子目錄放了兩個 SKILL 資料夾。層層往下：marketplace 裝 plugin，plugin 裝 SKILL，SKILL 裝判準與參考資料。

三、架構決策：先做一個階段，不做全流程

想清楚這兩個概念之後，第一個要決定的不是內容，是形狀。派了一個規劃用的 agent，讀過網站內容、查過 Claude Code 的 plugin marketplace 官方格式，回來給了兩個決定：

  1. 先做單一階段起步：只挑研究問題發想這個階段做稽核，不貪心做「從發想到口試」的全流程 SKILL。理由很直接——範圍越大，判準之間打架的機率越高，先驗證一個階段能不能跑通，比一開始就攤大餅划算。
  2. 用 plugin marketplace 格式：一個 marketplace repo 裡放一個 plugin，plugin 底下放多個 SKILL 資料夾。以後要加下一個階段（例如文獻回顧稽核），就是往同一個 plugin 底下加一個新的 SKILL 資料夾，不用重新設計架構。

這個決定後來證明是對的：中途實際加了第二個 SKILL，完全沒有動到既有結構，只是多開一個資料夾。

四、SKILL 一：研究問題稽核怎麼做出來的

第一個做的 SKILL，管的是「這個研究問題站不站得住腳」，跟文字寫得好不好無關。

素材來源：網站裡講研究問題怎麼問、假說怎麼推導、研究架構怎麼搭的頁面，加上研究缺口有哪五種分類的整理，還有提示詞範本頁裡「研究點子的價值與可行性審查」那一段角色扮演式的壓力測試提示詞。這些內容本來是寫給人讀的散文加檢查清單，同學得自己一條一條對照著看。

提煉過程：把這些內容轉譯成一套「一次跑完、不分輪次」的稽核流程，總共拆成七個檢查點——研究缺口分類、收斂程度、題目定案六問、六種壞題目長相比對、研究問題句型與常見錯誤、目的到結論的一致性檢查鏈、對抗式審查。每個檢查點都要求輸出明確的「通過／不通過／不適用」判定，不能只給模糊的感想。

設計上的一個關鍵決定：這個 SKILL 明確不做「陪同學從零發想題目」這件事。如果同學連一個模糊方向都沒有，SKILL 會直接說「這個工具是用來稽核已經有的想法，不是幫你發想」，然後停下來，不勉強往下跑判準。稽核跟發想是兩件不同的事，硬要一個 SKILL 兩件都做，通常會兩件都做不好。

後來的調整：使用者用過初版稽核報告後，覺得只列出「不通過／不確定」的問題清單不夠——知道哪裡有問題，跟知道怎麼解決問題，中間還有一段距離。這個調整的細節見第六節。

五、SKILL 二：學術寫作品質稽核怎麼做出來的

第二個做的 SKILL，管的是「這段文字寫得對不對、像不像人寫的、論證撐不撐得住」，跟研究設計邏輯無關，兩者刻意分工、互不重疊。

素材來源：學術中文寫作紀律整頁——因果動詞紀律、句子的構句原則、台灣學術用語對照表、APA 7 中文化格式、連接詞與標點慣例、去 AI 感的十二個特徵。這一頁本來就整理得夠完整，是這次提煉起來最直接的素材。

提煉過程：把原本頁面裡的替換表、grep 自檢指令、正反例整理成一個「單輪結構化輸出」的判準庫——同學貼一段文字進來，一次跑完全部判準，輸出一份標明嚴重程度、原句、問題、改法的清單，不追問、不分多輪。

中途的一次規則修正：草稿寫進 SKILL 的第一版，把「橫斷面研究不能寫因果」的規則照搬，而且搬得比原意更死——「影響」跟「導致」一樣被列進了同一張禁用詞清單。使用者看過草稿後指出這是錯的：問卷調查在同時符合三個條件時——理論文獻支持因果方向、用迴歸或路徑分析明確區分自變數與依變數、模型中控制了背景變數——寫「具有顯著正向影響」是可以接受、甚至是安全專業的慣例寫法，不該一律判定不通過。真正該抓的問題，是同一句話或同一節裡因果語言與相關語言前後矛盾，而不是「用了『影響』這個詞」本身。這個修正同時套用回網站正文與 SKILL 本身，兩邊的判準現在是一致的。

這段的教訓

先寫死一條規則，再被使用者的實務經驗糾正，這件事會反覆發生，不是寫錯一次就永遠不會再錯。規則寫得越死、越像非黑即白的禁用詞清單，越容易忽略「有條件允許」這種真實世界常見的中間狀態。

評測後補的一個輸出格式缺口：見下一節。

六、用 skill-creator 做評測：誠實面對「差異不大」

兩個 SKILL 都寫完規則，不代表真的有用。使用者提醒了一件容易被忽略的事：要檢查的不只是「觸發時機準不準」（該用的時候有沒有自動叫用），還有「用了之後輸出品質真的比較好嗎」。這兩件事都不能靠感覺判斷。

於是叫用了 Anthropic 官方的 skill-creator plugin，對兩個 SKILL 各自跑了一次完整的評測流程：設計一組測試案例、平行跑「有 SKILL」跟「沒有 SKILL 的基準版」兩條線做比較、用可量化的判準逐項打分、最後產出一份 benchmark 報告。

評測結果誠實得有點意外：Sonnet 5 本身對這類任務的基礎能力並不弱，SKILL 帶來的差異化價值，不是「解鎖一個模型原本做不到的能力」，而是保證判準的完整覆蓋、把用詞固定在同一套判準庫裡、讓輸出格式一致到可以規模化比較。換句話說，SKILL 的價值更接近「品管流程」，不是「能力升級」。

評測過程也真的在學術寫作品質稽核那個 SKILL 上抓到一個產品缺口：報告只列出診斷出來的問題清單，漏了一項同學實際會需要的輸出——把診斷出來的問題整合成一句可以直接拿去用的完整修改句。單看問題清單，同學還是得自己動手把好幾條建議兜成一句話；補上這個輸出項之後，才算真正把「知道哪裡錯」跟「怎麼改」接起來。

這段的教訓

評測前先假設「SKILL 一定比較好」是一種偷懶。跑完才知道差異可能沒有想像中大，這個誠實的結果本身就是有價值的資訊——它告訴你 SKILL 該往哪個方向優化（一致性與覆蓋率），而不是往哪個方向自我感覺良好。

七、給研究問題稽核加的逐項引導功能

初版的研究問題稽核 SKILL 跑完，只會輸出一份「通過／不通過／不確定」的問題清單。使用者用過之後回饋：知道哪裡有問題，跟知道怎麼把問題解決，中間還有一段距離。清單列完就結束，同學拿到一堆紅字，還是不知道該怎麼下手。

於是加了第二階段：報告結尾主動邀請使用者「要不要一項一項帶你想清楚」，使用者同意後才切換成引導模式——依邏輯先後排序待處理項目，一次只問一項，避免同一個問題來回問超過兩次導致卡死，答不出來就先記下待查證，往下一項走。這個設計刻意跟第一階段的「一次跑完全部判準」分開，不混在一起，是因為兩者的節奏根本不一樣：稽核要快、要一次看到全貌；引導要慢、要一次只處理一件事。

八、最終產出：同學怎麼安裝

完成的東西是一個獨立的 marketplace repo——wayhong0928/mis-thesis-skills（MIT 授權，公開）——裡面放一個 plugin（thesis-toolkit），plugin 底下有兩個 SKILL：研究問題稽核，跟學術寫作品質稽核。兩個 SKILL 可以先後套用在同一份草稿上，互不重疊。

不同介面的安裝方式不一樣，因為不是每個介面都支援 plugin marketplace 這套格式：

介面 安裝方式
Claude Code 先加入 marketplace，再安裝裡面的 plugin：/plugin marketplace add wayhong0928/mis-thesis-skills，接著 /plugin install thesis-toolkit@mis-thesis-skills
Claude Cowork Customize → Plugins → Add marketplace，在欄位填入 wayhong0928/mis-thesis-skills，走 GUI 流程；跟 Claude Code 是同一套 marketplace 格式，只是介面換成圖形化
Claude.ai 網頁版 不支援 marketplace 格式。要把單一 SKILL 資料夾另外包成 zip，在 Customize → Skills 手動上傳。另外要注意 Claude.ai 的 description 欄位上限只有 200 字元，比 Claude Code 短，同一份 SKILL 搬過去可能要把 description 重寫得更精簡
OpenAI Codex 官方也支援 SKILL 這個開放格式（name＋description 是雙方相容的核心欄位），但走的是不同路徑：Codex 讀 .agents/skills/（或 $HOME/.agents/skills、/etc/codex/skills），不是 Claude Code／Cowork 用的 plugin marketplace 機制——marketplace 是 Claude 生態系專屬的打包與發布方式，不等於 SKILL 格式本身。同學如果用 Codex，可以把 SKILL 資料夾放進 .agents/skills/，或建一個 symlink 指向 Claude Code 那份，兩邊共用同一份檔案；Codex 有自己的安裝指令可以從其他 repo 裝 SKILL，只是不能用 /plugin install 那套。Claude Code 專屬的進階欄位（例如工具權限白名單）Codex 不支援，但不會因此壞掉，只是少了那部分免詢問權限的體驗

為什麼要特別列這張表

同一份 SKILL 在不同介面能不能裝、怎麼裝，取決於各家支援哪一層格式——SKILL.md 本身是開放標準，Claude 生態系用的 plugin marketplace 是另一層打包與發布方式，兩者不能混為一談。動手打包之前先查清楚目標同學實際用的是哪個介面、走哪一層，免得包好了才發現裝不上去。

九、如果你也想把教材變成 SKILL：一套可以照抄的步驟

以下這套步驟，是從上面的實作過程回頭整理出來的，跟前面的具體內容無關，任何「把一份你已經整理好的教材或檢查清單，變成可重複執行的 SKILL」的任務都適用。

1. 盤點原料

先把所有可能用得上的來源列出來：網站正文、你自己的私人筆記、你手上已經在用的提示詞範本。每一項標明「涵蓋了什麼、缺了什麼」。原料盤點不清楚，後面每一步都會做白工——例如漏掉某個來源，寫到一半才發現規則不完整，得回頭重寫。

2. 去重與分層

同一件事在不同來源裡可能出現不只一次，措辭還不一樣。分層的原則是：底層放跨情境都成立的通用規則，上層放特定情境才適用的細規則，上層可以覆寫底層，但重複的內容只留一處。分層之後，你才看得出來哪些是「這個 SKILL 一定要收」，哪些是「這個情境才需要，換個情境就該拿掉」。

3. 授權與來源檢查

任何萃取自他人著作、部落格、課程教材的內容，在動手寫進 SKILL 之前先確認授權條款允許到什麼程度。不確定的時候，先當作「不能收進公開版本」處理，而不是先收進去、等有人反映才處理。查不到明確聲明時，去查原始出處的官方頁面或授權頁，這是查得到的事實，不用用猜的。

4. 可檢查化

把抽象的原則改寫成「能被逐條判定通過或不通過」的形式，而不是一段籠統的敘述。例如「文字要通順」沒辦法檢查，「連續三句字數差在 4 字以內要標記」就可以。判準能不能被明確判定，直接決定這個 SKILL 用起來是不是每次都一致，還是每次都憑感覺。

5. 正反例與紅線標注

容易被誤解的規則，配一組具體的例子：什麼情況該判不通過，什麼情況其實是例外、可以放行。規則用講的容易顯得抽象，配上例子才真正可執行——這也是最容易被漏掉、但最值得花時間補的一步。

6. 用真實評測驗證，不要只憑直覺

寫完不代表有用。找一組測試案例，實際比較「有這個 SKILL」跟「沒有這個 SKILL」的輸出差在哪裡，用可量化的方式打分，不要只憑感覺覺得「應該有幫助」。如果評測結果顯示差異不大，誠實面對這個結果，去想 SKILL 真正的價值在哪裡（通常是一致性與覆蓋率，而不是能力升級），而不是硬凹一個好看的結論。

7. 分層發布

公開發布的部分，嚴格收窄到「可以獨立溯源、跟任何有授權疑慮的來源無關」的範圍；跟個人專屬經驗、他人原創框架綁在一起的部分，留在自己的私人筆記裡，不要為了讓 SKILL 看起來更完整就一起打包對外發布。

本頁重點回顧

  • 起點是網站自己早就提過的一句話：連續貼第三次同樣的提示詞，就該包成 SKILL。這次是親自示範一次完整的過程。
  • SKILL 是資料夾＋SKILL.md，靠 description 決定觸發時機，用 progressive disclosure 分層展開內容，平常不佔用對話脈絡；Plugin 是把多個 SKILL 包起來、可安裝可分享的單位；Marketplace 是收錄多個 plugin 的獨立 repo，同學要先加 marketplace 再裝 plugin。
  • 架構決策先做窄後做寬：單一階段起步，用 plugin marketplace 格式，未來加階段只是加資料夾，不用重新設計。
  • 兩個 SKILL 分工清楚：一個管研究設計邏輯站不站得住腳，一個管文字與論證品質，互不重疊，也各自從不同頁面提煉素材。
  • 規則寫得太死一樣會出錯：因果動詞規則被使用者的實務經驗糾正，教訓是規則要留有條件允許的空間，不是非黑即白的禁用詞清單。
  • 評測不能省，而且要誠實面對「差異不大」這種結果——SKILL 的價值常常是一致性與覆蓋率，不是能力升級；評測也真的抓到一個輸出格式的缺口並修好。
  • 稽核報告只列問題清單還不夠，主動邀請、同意才進入的逐項引導模式，是把「知道有問題」帶到「解決問題」的關鍵一步。
  • 同一份 SKILL 在不同介面能不能裝、怎麼裝不一樣，動手包裝前先確認目標介面支不支援 plugin marketplace 格式。
  • 把教材變成 SKILL 的七步，跟具體內容無關：盤點原料、去重分層、授權檢查、可檢查化、正反例、真實評測、分層發布。
